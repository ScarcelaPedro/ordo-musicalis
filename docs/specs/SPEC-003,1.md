# SPEC 3.1 — Adaptação do Design ao Domínio do Sistema

Projeto: Sistema de Gestão de Escalas Paroquiais
Objetivo: Adaptar o Design System e a referência visual definida para a realidade completa do sistema, antes da implementação definitiva.

---

# 1. CONTEXTO

O sistema não será exclusivo para músicos.

O sistema será utilizado para gerenciamento das escalas de diferentes servidores da paróquia.

Exemplos de servidores:

- Acólitos;
- Ancilas;
- Coroinhas;
- Ministros da Eucaristia;
- Leitores;
- Músicos;
- Cantores;
- Salmistas;
- Cerimoniários;
- outros servidores/ministérios cadastrados no sistema.

Portanto, a interface deve ser construída como uma plataforma de gestão de servidores e escalas paroquiais, e não como um sistema exclusivamente musical.

---

# 2. PRINCÍPIO CENTRAL

A interface deve funcionar para diferentes ministérios sem precisar criar uma interface completamente diferente para cada um.

O sistema deve possuir:

- estrutura visual consistente;
- componentes reutilizáveis;
- linguagem comum;
- suporte a diferentes tipos de servidores;
- possibilidade de crescimento futuro.

O conceito central é:

"Uma plataforma única para organizar as escalas e os servidores da paróquia."

---

# 3. REFERÊNCIA VISUAL

A interface apresentada como referência deve ser utilizada como inspiração para:

- estrutura;
- proporções;
- densidade;
- hierarquia;
- organização;
- espaçamento;
- uso de cards;
- sidebar;
- topbar;
- calendário;
- tipografia;
- indicadores;
- estética geral.

Não copiar literalmente os conteúdos da referência.

Adaptar a estrutura para o domínio real do sistema.

---

# 4. SIDEBAR

A ordem atual das opções do sistema deverá ser preservada.

Não reorganizar a sidebar apenas para reproduzir a referência visual.

A prioridade é:

1. manter a arquitetura de navegação já existente;
2. aplicar o novo Design System;
3. melhorar clareza e hierarquia;
4. melhorar estados ativo/hover/focus;
5. melhorar responsividade.

A sidebar deve manter a ordem atualmente definida no sistema.

---

# 5. DASHBOARD ADMINISTRATIVO

A referência visual apresentada corresponde ao Dashboard administrativo.

Esse Dashboard poderá possuir uma quantidade maior de informações.

O objetivo é permitir que o administrador/coordenador tenha uma visão geral da situação das escalas.

Elementos possíveis:

- próxima celebração;
- calendário;
- próximas celebrações;
- cobertura das funções/ministérios;
- avisos;
- pendências;
- indicadores administrativos.

A composição final deve respeitar os dados e funcionalidades realmente existentes no sistema.

Não inventar informações apenas para preencher espaço visual.

---

# 6. DASHBOARD DO USUÁRIO COMUM

O usuário comum não deve receber a mesma densidade de informações do administrador.

O Dashboard do usuário comum deverá ser simplificado.

Prioridade:

1. próxima escala;
2. próximas escalas;
3. confirmações pendentes;
4. disponibilidade;
5. comunicações relevantes;
6. repertório/conteúdo quando aplicável.

Exemplo conceitual:

------------------------------------------------

Bom dia, João! 👋

Sua próxima escala

Domingo, 24 de agosto
10:00 — Missa Solene

Igreja Matriz

Função:
Leitor

[Ver escala]

10:00
Missa Solene

31 AGO

------------------------------------------------

Pendências

Você possui 1 escala aguardando confirmação.

[Ver pendências]

------------------------------------------------

A interface deve responder rapidamente:

"O que eu preciso saber ou fazer agora?"

---

# 7. DASHBOARD POR PERFIL

O sistema deverá possuir uma experiência adequada ao perfil.

## Administrador/Coordenador

Priorizar:

- visão geral;
- próximas celebrações;
- situação das escalas;
- cobertura;
- pendências;
- conflitos;
- avisos;
- ações administrativas.

## Usuário/Servidor

Priorizar:

- minha próxima escala;
- minhas próximas escalas;
- confirmações;
- disponibilidade;
- comunicações;
- conteúdos relevantes.

Não exibir informações administrativas desnecessárias ao usuário comum.

---

# 8. CALENDÁRIO

IMPORTANTE:

O calendário apresentado na referência visual não deve ser tratado como o calendário principal do Dashboard.

O calendário é uma representação do calendário litúrgico utilizado pelo sistema e deverá permanecer como componente próprio da experiência definida anteriormente.

A implementação deve respeitar a arquitetura atual.

---

# 9. CALENDÁRIO LITÚRGICO

Os indicadores coloridos presentes no calendário representam o TEMPO LITÚRGICO.

Eles NÃO representam:

- disponibilidade;
- prioridade;
- status da escala;
- nível de importância;
- confirmação;
- função.

Portanto, a cor do indicador deve ser interpretada exclusivamente como informação relacionada ao calendário litúrgico.

---

# 10. LEGENDA DO CALENDÁRIO

A legenda deverá deixar explícito o significado das cores.

Exemplo conceitual:

● Verde — Tempo Comum
● Roxo — Advento/Quaresma
● Branco — Natal/Páscoa/Festas apropriadas
● Vermelho — celebrações específicas
● Rosa — celebrações específicas
● Especial — datas litúrgicas especiais

Os valores exatos devem utilizar as regras e dados já existentes no sistema.

Não criar uma nova classificação litúrgica.

---

# 11. MOBILE FIRST

O sistema possui uma abordagem Mobile First.

O calendário utilizado no sistema deve manter sua lógica própria para dispositivos móveis.

O calendário da experiência mobile NÃO deve ser tratado simplesmente como uma versão reduzida do calendário desktop.

A implementação deverá respeitar o comportamento atualmente definido no projeto.

---

# 12. DESKTOP

No desktop, o calendário poderá utilizar uma apresentação mais ampla quando isso melhorar a visualização.

Porém:

- não transformar o calendário em um componente excessivamente grande;
- não comprometer a hierarquia do Dashboard;
- não adicionar informações desnecessárias;
- manter a leitura dos tempos litúrgicos.

---

# 13. SISTEMA MULTIMINISTÉRIO

A interface deverá funcionar para diferentes tipos de servidores.

Exemplo:

Uma escala pode possuir:

- Acólito;
- Leitor;
- Ministro da Eucaristia;
- Músico;
- Cantor;
- Salmista;
- Cerimoniário.

A interface não deve assumir que toda escala possui músicos.

---

# 14. REPRESENTAÇÃO DE MINISTÉRIOS

Sempre que o sistema precisar representar uma função ou ministério, utilizar dados reais provenientes do sistema.

Exemplo:

Função:
Ministro da Eucaristia

Função:
Leitor

Função:
Acólito

Função:
Músico

Função:
Salmista

Não criar categorias fictícias apenas para fins visuais.

---

# 15. COBERTURA DOS MINISTÉRIOS

O componente de cobertura apresentado na referência visual pode ser utilizado no Dashboard administrativo.

Porém, ele deve representar os ministérios reais do sistema.

Exemplo conceitual:

Cobertura dos Ministérios

Leitores
████████████░░
12/16 escalados

Ministros da Eucaristia
████████░░░░
8/10 escalados

Acólitos
██████████░░
14/16 escalados

Música
████████████
14/16 escalados

Os valores devem ser provenientes dos dados reais.

---

# 16. FLEXIBILIDADE

O componente deve suportar diferentes quantidades de ministérios.

Não assumir que sempre existirão quatro categorias.

Caso existam mais categorias:

- utilizar lista;
- utilizar scroll interno quando apropriado;
- utilizar agrupamento;
- ou apresentar apenas os itens mais relevantes.

Não deformar o Dashboard para acomodar dados excessivos.

---

# 17. ESCALA

A entidade central do sistema é a escala/celebração.

A interface deve tratar a escala como um objeto que pode envolver diversos ministérios.

Estrutura conceitual:

Celebração

↓

Escala

↓

Funções

↓

Servidores

Portanto:

uma celebração pode possuir vários ministérios;

um ministério pode possuir várias funções;

uma função pode possuir um ou mais servidores, conforme as regras existentes.

---

# 18. DETALHES DA ESCALA

A tela de detalhes deve apresentar de forma clara:

- celebração;
- data;
- horário;
- local/comunidade;
- informações litúrgicas;
- ministérios;
- funções;
- servidores;
- status;
- observações;
- demais informações existentes.

Não priorizar apenas a informação musical.

---

# 19. IDENTIDADE VISUAL

A identidade visual deve permanecer:

- sóbria;
- litúrgica;
- moderna;
- profissional;
- acolhedora;
- acessível.

A referência visual possui forte predominância azul.

Essa linguagem pode ser utilizada como base, desde que continue coerente com a identidade visual definida anteriormente para o projeto.

---

# 20. ELEMENTOS LITÚRGICOS

Elementos religiosos podem aparecer na interface, porém com moderação.

Exemplos:

- cruz;
- arquitetura da igreja;
- símbolos litúrgicos;
- elementos relacionados ao calendário litúrgico.

Utilizar esses elementos como apoio visual.

Não transformar a interface em uma composição excessivamente decorativa.

---

# 21. CARDS

Cards devem ser utilizados para agrupar informações relacionadas.

Exemplos:

- próxima celebração;
- próxima escala;
- avisos;
- pendências;
- cobertura;
- informações resumidas.

Não transformar todas as informações da interface em cards.

Cards devem possuir função estrutural.

---

# 22. HIERARQUIA

Cada tela deve possuir:

1. contexto;
2. informação principal;
3. ação principal;
4. informações secundárias;
5. ações auxiliares.

A interface não deve apresentar todos os elementos com o mesmo peso visual.

---

# 23. ÍCONES

Os ícones devem:

- possuir estilo consistente;
- possuir tamanho coerente;
- reforçar significado;
- não substituir texto quando o significado não for óbvio.

Não utilizar ícones puramente decorativos em excesso.

---

# 24. CORES DE STATUS

IMPORTANTE:

Não misturar:

CORES DO TEMPO LITÚRGICO

com

CORES DE STATUS DO SISTEMA.

São conceitos diferentes.

Exemplo:

Indicador verde do calendário:

→ informação litúrgica.

Badge verde:

→ pode representar confirmação/sucesso.

Essas duas coisas não devem ser interpretadas como equivalentes.

---

# 25. ACESSIBILIDADE DAS CORES

Como as cores do calendário possuem significado litúrgico:

não depender exclusivamente da cor para transmitir informações essenciais.

Quando necessário:

- legenda;
- tooltip;
- texto;
- indicação visual complementar.

---

# 26. USUÁRIO COMUM

O usuário comum não deve receber:

- indicadores administrativos desnecessários;
- excesso de estatísticas;
- informações de outros servidores;
- informações internas de gerenciamento.

A experiência deve ser focada naquilo que diz respeito a ele.

---

# 27. ADMINISTRADOR

O administrador deve possuir uma visão mais abrangente.

Porém, mesmo o Dashboard administrativo deve respeitar hierarquia.

Não colocar dezenas de indicadores simplesmente porque existe espaço.

Cada componente deve responder a uma necessidade real.

---

# 28. RESPONSIVIDADE

Desktop:

Layout mais amplo.

Tablet:

Layout adaptado.

Mobile:

Layout simplificado.

Não reduzir simplesmente o desktop.

A interface deve reorganizar informações de acordo com o espaço disponível.

---

# 29. REFERÊNCIA VISUAL + PRODUTO REAL

A imagem de referência deve ser interpretada como:

LINGUAGEM VISUAL

e não como:

LAYOUT OBRIGATÓRIO.

O resultado final deve combinar:

REFERÊNCIA VISUAL

+

DESIGN SYSTEM

+

ARQUITETURA EXISTENTE

+

REGRAS DE NEGÓCIO

+

NECESSIDADES DOS USUÁRIOS.

---

# 30. NÃO ALTERAR A ARQUITETURA ATUAL SEM NECESSIDADE

A implementação não deve modificar:

- ordem da sidebar;
- estrutura de permissões;
- regras de negócio;
- entidades;
- APIs;
- banco;
- fluxos existentes;

apenas para reproduzir a referência visual.

---

# 31. CRITÉRIOS DE ACEITE

A adaptação será considerada correta quando:

- [ ] O sistema puder representar diferentes ministérios.
- [ ] A interface não assumir que o sistema é exclusivamente musical.
- [ ] A sidebar mantiver a ordem atual.
- [ ] O Dashboard administrativo possuir maior densidade de informações.
- [ ] O Dashboard do usuário comum for simplificado.
- [ ] O calendário continuar respeitando a experiência Mobile First existente.
- [ ] O calendário não for confundido com o Dashboard.
- [ ] Os indicadores coloridos forem tratados como Tempo Litúrgico.
- [ ] Cores litúrgicas não forem utilizadas como status administrativo.
- [ ] A cobertura puder representar diferentes ministérios.
- [ ] A interface continuar responsiva.
- [ ] O Design System permanecer consistente.
- [ ] Nenhuma regra de negócio for alterada.

---

# 32. DIRETRIZ FINAL

O sistema NÃO deve se tornar:

"um sistema de músicos com suporte a outros servidores."

Ele deve se tornar:

"um sistema paroquial de gestão de escalas, capaz de atender diferentes ministérios e servidores."

A música é um dos ministérios.

Acólitos, Ministros da Eucaristia, Leitores, Coroinhas e demais servidores fazem parte do mesmo ecossistema.

A UI deve refletir essa realidade.

# 34. RESULTADO ESPERADO

O agente deverá conseguir implementar a nova UI utilizando a referência visual fornecida como direção estética, mas respeitando integralmente:

- o sistema existente;
- a arquitetura;
- os fluxos;
- os usuários;
- os diferentes ministérios;
- o calendário litúrgico;
- a experiência Mobile First;
- as regras de negócio.

Não reproduzir a imagem literalmente.

Adaptar o conceito ao produto real.
